# High-frequency response — 44.1 kHz / 24-bit through BruteFIR

## Scope

The existing counter WAVs prove sample identity, but their near-silent low-bit
pattern is not a frequency-response probe. The rate-mismatch tones stop at 1499
Hz. This test targets the reported "boxy, compressed, less air" symptom with
equal-amplitude tones at 1, 4, 8, 12, 16 and 19 kHz.

The tones play simultaneously for 15 seconds. The analyser ignores FIR
start-up and uses only the settled last two seconds. A 524288-tap filter retains
about 11.9 seconds of input history at 44.1 kHz, but **that is not playback
latency**. Partitioned convolution starts producing audio after approximately
one partition: about 0.19 seconds for 8192 samples or 0.74 seconds for 32768
samples. Waiting a full impulse length only ensures every coefficient has
contributed to the steady test tones.

The music route is included end to end:

```text
MPD -> snd-aloop / virtual_oss -> BruteFIR + real room filter -> USB -> DAC
```

## 1. Common 44.1 kHz / 24-bit source

The generated repository fixture uses these defaults:

```sh
python3 scripts/gen-high-frequency-wav.py \
    tests/high-frequency-test-44100-s24-stereo.wav
```

It is signed 24-bit PCM stereo at 44,100 Hz, matching the Mahler recording's
source format. Each tone is -30 dBFS peak. The sum uses deterministic
low-crest-factor phases and has ample headroom. This is audible: turn the
amplifier down before playing it through loudspeakers.

## 2. Reproduce the live 44.1 -> 192 kHz condition

During the motivating playback, `drc.sh status` reported source `44100:24:2`
while both `virtual_oss` and BruteFIR ran at 192 kHz. The primary run therefore
keeps the 44.1 kHz / 24-bit source and starts the same real 192 kHz geometry and
variant on each boot. Substitute the geometry used for listening if different.

FreeBSD:

```sh
omdrc geometry 120.green
omdrc 192000 @v1-fdw6
python3 scripts/bitperfect_runner.py \
    --source mpd --route drc --drc-output DRC-native \
    --reference capture --allow-resample \
    --input tests/high-frequency-test-44100-s24-stereo.wav \
    --out bp-results/high-frequency-120.green-v1-fdw6-192k-freebsd
```

Linux:

```sh
omdrc geometry 120.green
omdrc 192000 @v1-fdw6
python3 scripts/bitperfect_runner.py \
    --source mpd --route drc --drc-output DRC-native \
    --reference capture --allow-resample \
    --input tests/high-frequency-test-44100-s24-stereo.wav \
    --out bp-results/high-frequency-120.green-v1-fdw6-192k-linux
```

`--reference capture` is required because the real room filter changes the
source by design. `--allow-resample` permits and records the intentional rate
mismatch. MPD's resampler is not sample-deterministic between runs, so compare
this pair by response; a whole-sample null is not valid for these runs.

Do not require Linux and FreeBSD RAW coefficient hashes to match. The runtime
RAWs are regenerated from the same canonical filter WAVs by the host's SoX,
and the SoX versions differ. Verify the same geometry, design, source-WAV
hash, rate and attenuation, record both RAW hashes, then compare the measured
responses. Hash inequality identifies different generated bytes; it does not
by itself demonstrate an audible or frequency-response difference.

## 3. Measure the cross-OS response

Put both capture prefixes (`.wire.raw` plus `.json`) on one system:

```sh
python3 scripts/high-frequency-response.py \
    bp-results/high-frequency-120.green-v1-fdw6-192k-linux \
    bp-results/high-frequency-120.green-v1-fdw6-192k-freebsd \
    --json bp-results/high-frequency-120.green-v1-fdw6-192k-xos.json
```

The delta is `FreeBSD - Linux`. Each channel is normalized to its own 1 kHz
tone, removing constant capture gain and avoiding any assumption that the room
filter is flat. A negative delta at 8--19 kHz quantifies the suspected treble
loss. The default limit is 0.25 dB; change it with `--max-delta-db` if the
measurement chain warrants a wider tolerance.

The analyser estimates sample-clock error from 1 kHz before fitting all six
amplitudes, so a modest independent-ADC clock offset does not masquerade as
high-frequency attenuation.

## 4. Rate-matched control

Repeat on each OS with the same geometry at 44.1 kHz and omit
`--allow-resample`:

```sh
omdrc geometry 120.green
omdrc 44100 @v1-fdw6
python3 scripts/bitperfect_runner.py \
    --source mpd --route drc --drc-output DRC-native \
    --reference capture \
    --input tests/high-frequency-test-44100-s24-stereo.wav \
    --out bp-results/high-frequency-120.green-v1-fdw6-44k-matched-freebsd
```

Use `...-linux` on Linux, then compare those prefixes with the same response command.
This control separates an OS-path difference from the 44.1 -> 192 kHz
resampling condition. The existing whole-sample null is also valid for the
rate-matched pair when the coefficient provenance agrees.

## 5. Interpreting a pass

The runner captures host-side USB submissions, not the physical USB wire or
proof of DAC reception. A pass finds no meaningful relative treble roll-off at
the tested frequencies in the submitted PCM, but does not establish successful
delivery, DAC analogue response, or absence of electrical/noise interactions.
See `FREEBSD-UAUDIO-TRANSPORT-AUDIT-2026-09-14.md` for completion tracing and
the device-identity correction.

If USB passes while the audible difference remains, record the DAC output
through the same independent ADC, cabling, input gain and sample rate on both
boots, then give those PCM WAVs to the analyser. Whether the OKTO exposes any
usable capture interface must be determined from its actual descriptors; the
live measurements documented here used a Cambridge Audio DacMagic 100.

The Simon Rattle/Mahler passage remains useful for a final blind ABX of those
analogue captures. It is copyrighted and program-dependent, so it is neither a
calibrated response probe nor a repository fixture.
